# 팩 획득과 인기순 집계

## 배포 순서

1. 데이터베이스를 백업하고 Supabase SQL Editor 또는 프로젝트의 기존 마이그레이션
   절차로 `migrations/202610150001_pack_acquisitions.sql`을 적용합니다.
   기존 `shop_packs` 테이블(텍스트 ID), `profiles` 테이블(UUID ID, `role`),
   Supabase Auth 테이블이 있어야 합니다. 새 테이블과 RPC(앱에서 호출하는 서버 함수)는
   하나의 트랜잭션으로 생성됩니다.
   이어서 `migrations/202610150002_preserve_guest_acquisition_counts.sql`도 적용합니다.
   첫 번째 파일을 이미 적용했다면 두 번째 파일만 추가 실행합니다.
2. Authentication 설정에서 Anonymous Sign-Ins(익명 로그인)를 활성화합니다.
   기존 사용자 생성 트리거가 이메일 없는 익명 사용자도 허용하는지 확인합니다.
   공개 배포 전 익명 가입 제한과 CAPTCHA 설정도 검토합니다.
3. 일반 사용자가 `profiles.role`을 변경하거나 다른 사용자의 프로필을 수정할 수
   없는지 확인합니다. 서버는 이 역할 값을 기준으로 구매와 관리자 여부를 판단합니다.
4. 아래 SQL 테스트를 실행하고 스테이징 프로젝트에서 앱의 주요 동작을 확인합니다.
5. 마이그레이션과 인증 설정이 적용된 뒤 팩 획득 기능을 배포합니다.
   `get_pack_popularity()`가 없거나 호출에 실패해도 팩 목록은 표시됩니다.
   집계 정보를 불러오지 못하면 획득 수를 0으로 간주하지 않고 인기순을 비활성화합니다.

소스 코드 변경만으로 운영 데이터베이스의 SQL이나 대시보드 설정이 적용되지는 않습니다.

## 동작 방식

- 처음 실행하면 로그인 화면 없이 익명 Supabase 세션을 생성합니다.
- 무료 다운로드 또는 유료 구매에 성공하면 사용자·팩 조합별로 기록 1개를 생성합니다.
- `counted`에는 획득 당시 관리자 집계 제외 여부를 기록합니다. 이후 역할이 바뀌어도
  기존 기록은 바뀌지 않습니다. 같은 팩을 반복 획득해도 집계 수는 증가하지 않습니다.
- 인기순은 집계 대상 획득 수 내림차순이며, 동률이면 등록일 내림차순 → 제목 → ID
  순으로 정렬합니다.
- 새 팩을 획득하려면 서버에 연결되어 있어야 합니다. 마지막으로 불러온 팩 목록,
  계정별 보유 팩 ID, 코인 잔액은 오프라인 표시·편집을 위해 캐시합니다. 이미지는
  이미지 로더가 이전에 캐시한 경우에만 오프라인에서 사용할 수 있습니다.
  모든 이미지를 내려받는 완전한 오프라인 다운로드 기능은 아닙니다.
- 기존 기기에 저장된 보유 팩 ID는 계속 사용할 수 있으며 인기 집계에는 소급 반영하지
  않습니다. 이 내역은 기기의 사용 권한으로 유지하며, 서버에서 검증한 계정 소유권으로
  이전하지 않습니다.
- 익명 세션에서 이메일 계정으로 전환하기 전에 서버가 유효기간 7일의 이전 토큰을
  발급합니다. 기기는 재시도를 위해 이 토큰을 저장합니다. 이전 요청이 성공하면
  보유 팩과 서버 코인 잔액을 옮기고 중복 팩을 합치며, 이전 익명 ID로 추가 획득하는
  것을 차단합니다. 정식 계정만 이전을 완료할 수 있고, 성공한 요청을 반복해도
  중복 이전되지는 않습니다.
- 익명 획득 기록을 관리자 계정으로 옮겨도 획득 당시의 집계 여부를 유지합니다.
  관리자 로그인 상태에서 새로 획득한 기록만 집계에서 제외합니다.
  중복 보유 기록을 합칠 때는 어느 한쪽이라도 집계 대상이었다면 1회로 유지합니다.
  이전 함수가 이미 병합한 기록은 원래 집계 여부가 남아 있지 않으므로 이 수정으로
  자동 복구하지 않습니다. 확인 가능한 개별 기록만 별도로 정정해야 합니다.
- 캐시는 사용자 ID별로 분리합니다. 로그아웃 시 기존 계정의 팩을 새 익명 세션으로
  복사하지 않습니다. 기존 기기에 저장된 사용 권한은 계속 유지합니다.
- 앱을 재설치하면 새로운 익명 ID가 생성될 수 있습니다. 익명 사용자에 대해서는
  동일인이 평생 한 번만 집계되도록 보장할 수 없습니다.

## 유료 구매 연동 (전체 결제 흐름은 아직 미완성)

iOS 영수증 검증 코드와 앱 연결은 추가되었습니다. 실제 활성화에는 추가 SQL,
Apple 자격 증명 설정과 함수 배포가 필요합니다. 자세한 절차는
[iOS 코인 충전 설정](APPLE_BILLING.md)을 따릅니다. 아래 내용 중 영수증 검증 API와
결제 버튼 복원은 iOS에서 구현되어 있으며, Google Play와 기존 코인 이전은 남아 있습니다.

`acquire_pack`은 서버에서 가격과 관리자 여부를 확인합니다. 일반 사용자는 코인 지갑을
잠근 뒤 코인 차감과 보유 등록을 하나의 트랜잭션으로 처리합니다. 관리자는 코인을
차감하지 않고 획득할 수 있으며 인기 집계에서는 제외합니다.

기존 앱은 코인을 기기에만 저장했고 결제 영수증을 검증하는 서버가 없었습니다.
따라서 서버 검증 설정이 준비되기 전에는 앱에 “충전 준비 중”을 표시하고,
결제를 요청하거나 검증하지 않은 대기 거래를 완료 처리하지 않습니다. 기존 로컬 코인
잔액과 거래 내역의 저장 키는 유지하지만, 이 잔액을 서버 코인으로 인정하지는 않습니다.
클라이언트가 수정할 수 있는 잔액을 검증 없이 자동 이전하는 기능은 없습니다.

결제를 활성화하려면 다음 작업이 필요합니다.

1. Apple·Google 영수증을 검증하는 인증된 서버 API를 구현합니다.
2. 스토어 환경, 번들·패키지 ID, 상품 ID, 거래 유효성 및 소유권을 확인합니다.
   지급할 코인 수는 서버에서 관리하는 허용 상품 목록으로 결정합니다.
3. service-role 자격 증명으로
   `credit_verified_coins(user_id, globally_unique_store_transaction_id, amount)`를
   호출합니다. 이 자격 증명은 앱에 노출하면 안 됩니다. RPC는 검증된 거래마다
   코인을 한 번만 지급합니다.
4. 검증 성공 응답을 반환하고 앱에서 지갑 잔액을 다시 불러온 뒤 스토어 거래를
   완료 처리합니다. 앱 종료 후에도 안전하게 재시도할 수 있어야 합니다.
   환불과 익명 계정 이전 이후 제출된 영수증도 원래 거래의 소유 관계를 기준으로
   처리합니다.
5. 검증된 스토어 거래 내역 또는 고객 지원 기록을 기준으로 기존 코인 잔액을 대조하고
   이전합니다.
6. `src/app/coin.tsx`의 결제 요청과 정상 결제 버튼 문구를 복원합니다.

## 테스트

테스트는 PGlite의 PostgreSQL 엔진과 최소한의 인증·상점 스키마를 사용하며 원격
데이터베이스를 수정하지 않습니다. 별도의 테스트 디렉터리에 `@electric-sql/pglite`를
설치하고 모듈의 절대 경로를 전달합니다.

```sh
PGLITE_MODULE=/path/to/node_modules/@electric-sql/pglite/dist/index.js node --test supabase/tests/pack-acquisitions.test.mjs
node --test supabase/tests/shop-client.test.cjs
npx tsc --noEmit
```

SQL 테스트는 중복 획득, 비활성 팩, 잔액 부족, 쓰기·코인 지급 권한, 관리자 제외,
병합 시 중복 제거, 토큰 재사용, 지갑 처리의 멱등성(같은 요청을 반복해도 한 번만 반영)을
확인합니다. 스테이징 환경에서는 실제 회원가입·이메일 인증, RLS·프로필 정책,
여러 클라이언트의 동시 요청, 네트워크 중단, 실기기 동작을 추가로 확인해야 합니다.
